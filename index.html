DevSecOps · Sword · 2026

Enterprise multi-repo SonarQube scanning pipeline

Bash and Python automation that scans 15 repositories across 2 GitHub organisations into a self-hosted SonarQube and publishes results to Confluence. It runs with one command per repo and needs no per-repo configuration.

How it works

orchestrator.sh maps a repo to its SonarQube project through a JSON registry. It shallow-clones the branch with submodules and auto-detects the language (.NET/C#, JS/TS/Vue, Python or generic). It then runs the matching scanner, waits until the Compute Engine reports SUCCESS, publishes metrics and a full issue table to Confluence, and writes a full CSV export.

Engineering problems solved
  • Hidden hotspots: security hotspots were silently reporting zero. They now come from /api/hotspots/search, with TO_REVIEW tracked separately.
  • Wrong counts: issue counts were off by 38% (2,500 reported vs 4,054 real) because they were taken from the page-capped list. They now come from paging.total, with pagination.
  • Stale reports: a fixed sleep 30 sometimes published the previous scan's numbers. It was replaced with Compute Engine task polling.
  • Discarded lint findings: ESLint output was being thrown away. It's now wired in through sonar.eslint.reportPaths and makes up about 45% of findings on TypeScript projects.
  • Coverage gaps: added guards against silently degraded TypeScript analysis, uninitialised submodules and failed uploads. Branch-suffixed project keys work around Community Edition, which has no branch analysis.
  • Scan-integrity check: a diagnose-coverage.sh tool audits what a "green" scan actually covered.
